\section{Introduction}

\subsection{Purpose and scope}

Pogotrack is a research tool for reconstructing the trajectories of Pogobot swarms from video. It detects the position and orientation of each robot, links detections through time, and exports a tabular dataset that can be combined with the variables recorded by the robots, such as controller scores and weights.

This document is a practical guide rather than a complete software reference. It is written for a member of the team who has the raw files for an experiment and wants to reproduce the analysis from start to finish. The examples assume that commands are executed from the root of the Pogotrack repository.

The current maintainer is Keivan Amini, with contributions from the experimental and robotics teams, including Jérémy Fersula. Questions, corrections, and improvements are welcome.

\subsection{The analysis pipeline}

Pogotrack supports circular and rectangular arenas. The phototaxis workflow has currently been tested at ESPCI and uses separate processing for the dark and illuminated parts of the arena. Most experiment-specific settings, such as the arena geometry, number of robots, thresholds, and calibration, belong in YAML configuration files. Editing the detector code should not be necessary for a standard experiment.

A complete experiment normally provides the following files:

\begin{itemize}
  \item a dynamics video, for example \texttt{alpha10-4\_T100\_v2.mp4};
  \item an RGB-ID video, conventionally named by adding \texttt{id\_} before the dynamics-video name;
  \item \texttt{bkg.bmp}, the background image of the arena;
  \item a Feather file containing the internal variables recorded by the robots, usually named after the experiment.
\end{itemize}

The workflow has four stages:

\begin{enumerate}
  \item \textbf{Dynamics tracking.} The dynamics video is converted into one row per robot and frame, containing position, orientation, time, and a temporary TrackPy identity.
  \item \textbf{RGB-ID tracking.} The RGB-ID video is analysed to measure the red, green, and blue LED intensities for each robot during the flashing sequence.
  \item \textbf{Decoding and merging.} The RGB measurements are decoded into robot IDs and joined with the dynamics CSV and the controller data from the Feather file.
  \item \textbf{Summary figures.} The merged dataset is used to produce PNG and PDF summary slides containing controller, trajectory, light-occupancy, and space--time plots.
\end{enumerate}

The first two stages are independent video-processing jobs. The third stage connects their outputs, and the fourth stage is optional but useful for a quick quality check.

\section{Installation}

\subsection{System requirements}

Pogotrack supports CPython 3.11--3.13; Python 3.13 is recommended on Apple Silicon macOS. The versions used by the project are listed in \texttt{requirements.txt}. The workflow also needs the \texttt{ffmpeg} command-line program. The optional tmux launcher needs \texttt{tmux} as well.

On macOS with Homebrew, a typical installation is:

\begin{codeblock}
brew install python@3.13 ffmpeg tmux
cd /path/to/pogotrack
export DYLD_LIBRARY_PATH="$(brew --prefix expat)/lib${DYLD_LIBRARY_PATH:+:$DYLD_LIBRARY_PATH}"
python3.13 -m venv .venv
source .venv/bin/activate
python -m pip install -U pip
python -m pip install -r requirements.txt
\end{codeblock}

On some Homebrew installations, the \texttt{DYLD\_LIBRARY\_PATH} line is needed because \texttt{ensurepip} selects the system Expat library. After activating the environment, check the interpreter before running the pipeline:

\begin{codeblock}
python --version
which python
\end{codeblock}

The first command should report Python 3.11 or newer. The second should point inside \texttt{.venv/bin/}.

\warning{Pogotrack rejects Python versions older than 3.11. Always activate the project virtual environment first.}

Once the environment is active, all examples in this guide use \texttt{python}. If the environment is not active, replace \texttt{python} with the full path to the project interpreter, for example \texttt{.venv/bin/python}.

\section{Core analysis: one experiment}

This section describes each stage separately. Running the stages manually is useful when checking a new experiment or debugging a configuration. For routine analyses, the config-driven workflow in Section~\ref{sec:config-workflow} is more convenient.

\subsection{Launching standard tracking}

The main command analyses one video and writes the trajectory CSV given by \texttt{--output}:

\begin{codeblock}
source .venv/bin/activate

python -m main \\
  --video data/18-09-26/alpha10-4_T100_v2.mp4 \\
  --background data/18-09-26/bkg.bmp \\
  --output results/18-09-26/alpha10-4_T100_v2/alpha10-4_T100_v2.csv \\
  --config config/default.yaml
\end{codeblock}

For a phototaxis experiment, the default configuration uses the dark/light arena split and the ROI-based detection path. The standard CSV contains:

\begin{center}
\texttt{time, x, y, theta, particle}
\end{center}

Here \texttt{particle} is TrackPy's temporary identity. It is not the physical robot ID assigned to the robot in the experiment; that mapping is made later using the RGB-ID recording.

\subsection{Parallel processing of one video}

The dynamics video can be split into contiguous frame ranges and processed by multiple workers. This is different from running several experiments in parallel: here, several processes work on different parts of the same video.

For normal phototaxis tracking, independent frame chunks can be processed by multiple workers:

\begin{codeblock}
python -m main \\
  --video data/18-09-26/alpha10-4_T100_v2.mp4 \\
  --background data/18-09-26/bkg.bmp \\
  --output results/18-09-26/alpha10-4_T100_v2/alpha10-4_T100_v2.csv \\
  --config config/default.yaml \\
  --workers 2 \\
  --warmup-frames 50
\end{codeblock}

The video is split into contiguous frame ranges. Each worker receives context frames before its assigned range so that the phototaxis ROI detector can initialise its local state. Only the requested range is retained from each worker. The parent process then restores frame order and performs one global TrackPy linking pass, allowing temporary identities to continue across chunk boundaries.

The number of context frames is controlled by \texttt{--warmup-frames}; 50 is a reasonable starting value. Increase it if robots can move a long distance near a chunk boundary. The warm-up frames are processed again by neighbouring workers, so a small amount of redundant work is expected.

Multiprocessing has the following restrictions:

\begin{itemize}
  \item it is intended for standard dynamics tracking, including phototaxis;
  \item it cannot be combined with \texttt{RGB\_ID\_ANALYSIS: true};
  \item it cannot be combined with \texttt{--visualize};
  \item all workers must write to the same final output only through the parent process; do not start two jobs with the same output path;
  \item two workers are a sensible first benchmark on a laptop. More workers do not necessarily mean proportionally greater speed, because video decoding, memory bandwidth, and circle detection can become bottlenecks.
\end{itemize}

After a parallel run, compare its processing time and output with a sequential run on a representative video. In particular, check the number of rows, the number of detected robots per frame, and the continuity of trajectories around chunk boundaries.

\subsection{RGB-ID tracking}

The RGB-ID video is processed with \texttt{RGB\_ID\_ANALYSIS: true}. In normal use, \texttt{run\_pipeline.py} creates a temporary configuration, sets the expected robot count, and launches this step. For a direct run, first create a copy of the tracking configuration and enable RGB-ID analysis in that copy:

\begin{codeblock}
cp config/default.yaml config/rgb_id_experiment.yaml
\end{codeblock}

Then set \texttt{RGB\_ID\_ANALYSIS: true} and the correct \texttt{N\_POGO} in \texttt{config/rgb\_id\_experiment.yaml}, and run:

\begin{codeblock}
python -m main \\
  --video data/18-09-26/id_alpha10-4_T100_v2.mp4 \\
  --background data/18-09-26/bkg.bmp \\
  --output results/18-09-26/alpha10-4_T100_v2/RGB_ID.csv \\
  --config config/rgb_id_experiment.yaml
\end{codeblock}

The RGB-ID implementation writes \texttt{RGB\_ID.csv} in the directory containing the requested output path. It contains:

\begin{center}
\texttt{frame, time, id, x, y, theta, led\_x, led\_y, R, G, B}
\end{center}

The RGB values are measured around the estimated LED position. They are decoded into ternary symbols during the merging stage. RGB-ID processing is intentionally single-worker: the flashing sequence and the common robot pose must remain synchronised.

\subsection{Decoding IDs and merging controller data}

The merge script combines the dynamics CSV, the RGB-ID CSV, the RGB-ID calibration output, and the Feather file. It requires the delay between the dynamics and RGB-ID recordings in seconds. The RGB flashing start frame can be detected automatically when \texttt{--start-rgb-frame} is omitted.

For a manual merge, use a measured delay in place of \texttt{<seconds\_difference>}:

\begin{codeblock}
python postprocessing/process_id_trits.py \\
  --rgb-id-path results/18-09-26/alpha10-4_T100_v2/RGB_ID.csv \\
  --probe-path data/18-09-26/alpha10-4_T100_v2.feather \\
  --dyn-path results/18-09-26/alpha10-4_T100_v2/alpha10-4_T100_v2.csv \\
  --seconds-difference <seconds_difference> \\
  --expected-n-robots 64 \\
  --results results/18-09-26/alpha10-4_T100_v2/merged_alpha10-4_T100_v2.csv
\end{codeblock}

The script saves an intermediate \texttt{score\_calib\_pose\_id.csv} next to \texttt{RGB\_ID.csv} and writes the final merged dataset to the path given by \texttt{--results}. The config-driven workflow can estimate \texttt{seconds\_difference} automatically and is therefore recommended for routine processing.

\subsection{Generating summary slides}

Once the merged CSV exists, the slide generator can be run directly:

\begin{codeblock}
python postprocessing/experiment_slides_generator.py \\
  --csv results/18-09-26/alpha10-4_T100_v2/merged_alpha10-4_T100_v2.csv \\
  --video data/18-09-26/alpha10-4_T100_v2.mp4 \\
  --controller tanh \\
  --experiment-id alpha10-4_T100_v2 \\
  --output results/18-09-26/alpha10-4_T100_v2/alpha10-4_T100_v2
\end{codeblock}

This produces a PNG and a PDF with the same output base name. Optional plotting parameters, such as the light threshold, communication time, snapshot times, and controller parameters, can be added as command-line options. The available options are also exposed through the \texttt{slides.options} section of \texttt{postprocessing/pipeline.yaml}.

The main tracking settings are in \texttt{config/default.yaml}. The parameters below are the ones most likely to change when the arena or camera setup changes.

\texttt{MEMORY} & Number of frames for which a temporarily missing robot can retain its TrackPy identity. \\
\texttt{POGOBOT\_DIAMETER\_CM}, \texttt{PIXEL\_DIAMETER} & Pixel-to-centimetre calibration values. \\
\texttt{PHOTOTAXIS\_ANALYSIS} & Enables the dark/light split processing path. \\
\texttt{PHOTOTAXIS\_FAST} & Enables cached masks and ROI-based detection after initialization. \\
\texttt{PHOTOTAXIS\_THRESHOLDS} & Dark and light segmentation thresholds. \\

In practice, start with the arena geometry, robot count, foreground thresholds, phototaxis thresholds, and calibration values. Change these in YAML rather than editing the detection code. The postprocessing pipeline creates a temporary copy of the tracking configuration for each experiment and overwrites \texttt{N\_POGO} and \texttt{RGB\_ID\_ANALYSIS} there, so the shared default file is not modified.

\warning{It is assumed that the number of robots is fixed for an experiment. The detector uses the {N\_POGO} parameter when checking and recovering incomplete frames.}

\section{Relevant modules and classes}

\subsection{Core tracking}

\begin{itemize}
  \item \texttt{main.py}: parses the command line, constructs \texttt{VideoProcessor}, and selects standard, parallel, or RGB-ID processing.
  \item \texttt{video\_processing.py} in \texttt{src/}: contains the \texttt{VideoProcessor} class. Its principal methods are \texttt{process()}, \texttt{process\_parallel()}, and \texttt{process\_rgb\_id()}.
  \item \texttt{src/utils.py}: contains image preprocessing, contour and circle detection, pose estimation, pixel conversion, and tracking utilities.
  \item \texttt{src/plot\_helpers.py}: contains frame debugging, trajectory plotting, RGB-ID debug views, and GIF/contact-sheet helpers.
\end{itemize}

The standard path subtracts the background, applies the arena mask, detects robot candidates, estimates their orientation, and stores one row per robot and frame. TrackPy then links the temporary particles over time.

\subsection{Postprocessing modules}

\begin{itemize}
  \item \texttt{postprocessing/pipeline.yaml}: editable experiment list, paths, robot counts, merge settings, and slide settings.
  \item \texttt{postprocessing/run\_pipeline.py}: runs tracking, merging, and slide generation from that configuration.
  \item \texttt{postprocessing/process\_id\_trits.py}: detects the RGB flashing start, aggregates RGB windows, decodes ternary IDs, assigns real robot IDs, and merges controller data.
  \item \texttt{postprocessing/experiment\_slides\_generator.py}: creates PNG and PDF summary figures for step, Gaussian, and tanh controllers.
  \item \texttt{postprocessing/batch\_analysis\_tmux.sh}: optional interactive tmux launcher for independent experiment workers.
\end{itemize}

\section{Run all analysis all at once}
\label{sec:config-workflow}

\subsection{Configure an experiment}

Edit \texttt{postprocessing/pipeline.yaml} before starting a new analysis. An entry gives the date folder, dynamics video, robot count, optional per-video worker count, and any file-name overrides:

\begin{codeblock}
experiments:
  - id: alpha10-4_T100_v2
    date: 18-09-26
    video: alpha10-4_T100_v2.mp4
    n_robots: 64
    workers: 2
    probe_file: alpha10-4_T100_v2.feather
    outputs:
      normal: "{id}.csv"
      rgb_id: "RGB_ID.csv"
      merged: "merged_{id}.csv"
      slides: "{id}"
    merge:
      seconds_difference: auto
      start_rgb_frame: auto
    slides:
      enabled: true
      controller: tanh
\end{codeblock}

With \texttt{auto}, the merge step analyses the configured initial interval of the dynamics CSV for the first sustained population movement. It also searches the RGB-ID CSV for the LED onset. Replace either value with a numeric value if the automatic estimate is not suitable for a particular experiment. The optional \texttt{merge.auto} block controls the motion-detection thresholds.

The two worker settings have different meanings:

\begin{itemize}
  \item \texttt{workers} belongs to one experiment and controls how many processes analyse its dynamics video. \texttt{workers: 1} keeps the sequential implementation; \texttt{workers: 2} splits one video into two chunks.
  \item \texttt{batch.max\_workers} is global and controls how many experiments are launched concurrently by \texttt{run\_pipeline.py}.
\end{itemize}

Their product is a useful upper bound on the number of video-processing workers. For example, \texttt{batch.max\_workers: 2} and \texttt{workers: 2} may use up to four dynamics workers at once. Start conservatively, especially on a laptop, and increase the values only after benchmarking.

\subsection{Run all stages}

From the repository root, with the virtual environment active:

\begin{codeblock}
python postprocessing/run_pipeline.py
\end{codeblock}

The script runs the stages in this order:
\begin{enumerate}
  \item standard and RGB-ID tracking for each experiment;
  \item RGB-ID decoding and merging with the Feather data;
  \item PNG and PDF slide generation.
\end{enumerate}

Different experiments run concurrently as independent subprocesses according to \texttt{batch.max\_workers}. Within each experiment, the dynamics video can additionally use its own \texttt{workers} value. A temporary tracking configuration is created for each experiment, so \texttt{config/default.yaml} is left unchanged.

For a first complete test, it is sensible to use one experiment and conservative settings:

\begin{codeblock}
batch:
  enabled: true
  max_workers: 1

experiments:
  - id: alpha10-4_T100_v2
    date: 18-09-26
    video: alpha10-4_T100_v2.mp4
    n_robots: 64
    workers: 2
\end{codeblock}

Once this completes successfully, additional experiments can be enabled and \texttt{batch.max\_workers} can be increased.

\subsection{Run one stage or one experiment}

\begin{codeblock}
# Standard and RGB-ID tracking only
python postprocessing/run_pipeline.py --stage batch

# RGB-ID tracking only (standard tracking CSV must already exist)
python postprocessing/run_pipeline.py --stage rgb

# Merge existing tracking outputs
python postprocessing/run_pipeline.py --stage merge

# Generate slides from existing merged outputs
python postprocessing/run_pipeline.py --stage slides

# Restrict any stage to one configured experiment
python postprocessing/run_pipeline.py \\
  --stage merge \\
  --experiment alpha10-4_T100_v2

# Inspect commands without executing them
python postprocessing/run_pipeline.py --dry-run
\end{codeblock}

The \texttt{--stage batch} command runs standard dynamics tracking followed by RGB-ID tracking. It does not perform merging or slide generation. The \texttt{--stage rgb} command is useful when the dynamics CSV already exists and only the RGB-ID video needs to be reprocessed.

The output for one experiment is stored under:

\begin{codeblock}
results/<date>/<experiment>/
+-- <experiment>.csv                  # dynamics tracking output
+-- RGB_ID.csv
+-- score_calib_pose_id.csv          # RGB-ID decoding intermediate
+-- merged_<experiment>.csv          # final merged dataset
+-- <experiment>.png                 # summary figure
+-- <experiment>.pdf                 # summary figure
+-- tracking.log
+-- rgb_tracking.log
+-- merge.log
+-- slides.log
\end{codeblock}

\section{Understanding the merged data and slides}

The merged dataset contains the main quantities used for swarm analysis:

\begin{center}
\texttt{t, x, y, theta, q, w, id}
\end{center}

Here \texttt{t} is time after the detected offset, \texttt{x} and \texttt{y} are robot coordinates, \texttt{theta} is orientation, \texttt{q} and \texttt{w} are controller variables from the Feather file, and \texttt{id} is the decoded robot identifier. The exact time origin depends on the delay supplied to the merge step.

The slide generator includes:
\begin{itemize}
  \item the controller response panel;
  \item representative video frames at the initial, middle, and final times;
  \item the fraction of robots in the light region;
  \item per-robot and mean score/weight traces;
  \item relative density, weight, and score space-time fields.
\end{itemize}

The controller type is selected in the postprocessing configuration:

\begin{codeblock}
slides:
  enabled: true
  controller: tanh       # step, gaussian, or tanh
\end{codeblock}

Additional slide options, such as light threshold, communication time, snapshot times, bin counts, and controller parameters, can be supplied under \texttt{slides.options}.

\section{Troubleshooting checklist}

If an analysis fails or the result looks wrong, check the following:

\begin{enumerate}
  \item Confirm that the active interpreter is the project virtual environment and Python is at least 3.11.
  \item Confirm that the dynamics video, \texttt{id\_} RGB video, background image, and Feather file belong to the same experiment.
  \item Confirm that \texttt{N\_POGO} or \texttt{n\_robots} matches the number of robots actually recorded.
  \item Check arena centre, radius, foreground thresholds, and phototaxis dark/light thresholds.
  \item Inspect \texttt{tracking.log}, \texttt{rgb\_tracking.log}, and the terminal output before changing algorithm code.
  \item Run \texttt{--dry-run} to verify all generated paths and commands.
  \item If automatic timing detection is unsuitable for one experiment, replace one or both \texttt{auto} values with manual values in \texttt{pipeline.yaml}.
  \item If parallel and sequential runs differ near a chunk boundary, increase \texttt{--warmup-frames} for the direct command and compare the resulting trajectories again.
  \item If the computer becomes unresponsive during a batch run, reduce either \texttt{batch.max\_workers} or the per-experiment \texttt{workers} value.
\end{enumerate}

\important{Keep the raw input data unchanged. Write generated CSV files, logs, and figures under \texttt{results/}; keep reusable settings in YAML files.}
